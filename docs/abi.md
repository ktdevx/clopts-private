# ABI の互換性

この章は、共有ライブラリとしてビルドした CLOpts の ABI（バイナリ互換性）について、何をいつから保証するか、版番号とファイル名がどう決まるか、どの変更が互換を保ち、どの変更が互換を壊すかを示す。共有ライブラリを新しい版に差し替えてよいかを判断するときと、CLOpts への変更をレビューするときの基準である。

## 保証の範囲

- 共有ライブラリの ABI の後方互換は、1.0.0 から保証する。
- 0.x の間は、minor が上がるごとに ABI を壊してよい。0.x の間に保証するのは、同じ minor の中（patch だけが違う版の間）での後方互換だけである。
- 保証するのは後方互換である。つまり、古い版の CLOpts に対してビルドした利用側の実行ファイルやライブラリが、同じ SOVERSION を持つ新しい版の共有ライブラリと組み合わせたときに、再ビルドせずに動くことを保証する。
- 前方互換は保証しない。新しい版に対してビルドした利用側を、古い版の共有ライブラリで動かせるとは限らない（新しい版で足した関数を使っていれば動かない）。
- 静的ライブラリ（`CLOPTS_BUILD_SHARED=OFF`、既定の形式）は対象外である。静的ライブラリは利用側に取り込まれるので、版を上げるときは利用側を再ビルドする。

## 版と SOVERSION

CLOpts の版は `major.minor.patch` で、`CMakeLists.txt` の `project(clopts VERSION ...)` で決まる。共有ライブラリの SOVERSION（ABI の互換の単位）は、版から次の規則で決まる。

| 版 | SOVERSION | 例 |
|----|-----------|----|
| 0.x（1.0.0 未満） | `0.<minor>` | 0.1.0 と 0.1.3 は `0.1`、0.2.0 は `0.2` |
| 1.0.0 以降 | `<major>` | 1.0.0 と 1.4.2 は `1`、2.0.0 は `2` |

SOVERSION が同じ版の間では ABI の後方互換を保ち、互換を壊すときは SOVERSION を変える。

Linux では、共有ライブラリのファイル名と SONAME に SOVERSION が入る。たとえば 0.1.0 を共有ライブラリとしてビルドすると、次の 3 つができる。

```text
libclopts.so.0.1.0                         実体
libclopts.so.0.1 -> libclopts.so.0.1.0     SONAME（readelf -d で見える）
libclopts.so     -> libclopts.so.0.1       ビルド時のリンク用
```

利用側の実行ファイルには SONAME の `libclopts.so.0.1` が記録され、実行時にはその名前で共有ライブラリを探す。そのため、SOVERSION の違う共有ライブラリを取り違えて読み込むことはない。1.4.2 なら、実体は `libclopts.so.1.4.2`、SONAME は `libclopts.so.1` になる。

macOS でも同じように、ファイル名と install name に SOVERSION が入る（0.1.0 なら実体は `libclopts.0.1.0.dylib`、install name は `@rpath/libclopts.0.1.dylib`）。

## Windows の DLL 名

Windows では、DLL のファイル名に版が入らない。

- MSVC: `clopts.dll`（インポートライブラリは `clopts.lib`）
- MinGW-w64: `libclopts.dll`（インポートライブラリは `libclopts.dll.a`）

利用側の実行ファイルに記録されるのも、版のないこの名前である。そのため、Windows では SOVERSION の違う DLL を取り違えても、ファイル名では防げない。互換のない DLL が読み込まれると、起動時に関数が見つからずに失敗するか、関数の型や列挙値の違いによって誤った動作をする。

利用側の実行ファイルの横には、ビルドに使った CLOpts と同じ SOVERSION の DLL を置くこと。同じ SOVERSION の新しい版の DLL に差し替えるのはよいが、SOVERSION の違う版の DLL に差し替えるときは利用側を再ビルドする。

## macOS の互換版と現在版

macOS の共有ライブラリ（`.dylib`）には、互換版（compatibility version）と現在版（current version）の 2 つの版番号が埋め込まれる（`otool -L` で見える）。CLOpts はこれらを CMake の既定のまま、次のように決める（`MACHO_COMPATIBILITY_VERSION` と `MACHO_CURRENT_VERSION` は設定しない）。

- 互換版: SOVERSION から作る。0.x の間は `0.<minor>.0`（0.1.x なら `0.1.0`）、1.x の間は `1.0.0`、2.x の間は `2.0.0` になる。
- 現在版: `project(VERSION)` の版そのもの（1.4.2 なら `1.4.2`）になる。

互換版は SOVERSION と同じ単位でしか変わらず、1.0.0 以降は minor ごとには上げない。

macOS の動的リンカ（dyld）は、利用側に記録された互換版より現在版が小さいライブラリを読み込まない。互換版を minor ごとに上げないので、この仕組みは同じ SOVERSION の中の前方互換を守らない。新しい minor（たとえば 1.4）に対してビルドした利用側を古い minor（たとえば 1.2）のライブラリで動かすと、版の不一致として読み込みを断られるのではなく、1.4 で足した関数が見つからないとき（`Symbol not found`）に初めて失敗する。足した関数を使っていなければ、そのまま動く。これは「前方互換は保証しない」という方針どおりの挙動であり、Linux と Windows でも同じことが起きる。

## 互換を保つ変更

次の変更は ABI の後方互換を保つ。同じ SOVERSION のまま、minor（または patch）の版で入れてよい。

- 公開関数の追加
- 列挙の末尾への値の追加（既存の値はそのまま）
- 不透明型（公開ヘッダでは名前だけを宣言し、中身を見せない型）の内部の変更
- 公開関数の内部の挙動の修正（文書に書いた契約の範囲内のもの）

## 互換を壊す変更

次の変更は ABI の後方互換を壊す。

- 公開関数の削除・改名
- 公開関数のシグネチャの変更（引数・戻り値の型や数の変更）
- 既存の列挙値の変更・並べ替え・途中への値の挿入
- 公開ヘッダへの構造体・共用体の定義の追加（中身を公開すると、その大きさと配置が利用側のバイナリに焼き込まれる）
- 公開ヘッダの関数ポインタ型のシグネチャの変更

## 互換を壊すときの手順

互換を壊す変更は、版を次のように上げるときにだけ入れる。

- 1.0.0 以降: major を上げる（1.4.2 の次は 2.0.0）。SOVERSION は `1` から `2` に変わる。
- 0.x の間: minor を上げる（0.1.3 の次は 0.2.0）。SOVERSION は `0.1` から `0.2` に変わる。

SOVERSION が変わると、Linux と macOS では共有ライブラリのファイル名と SONAME（install name）も変わる。古い版に対してビルドした利用側は、古い SOVERSION の共有ライブラリを探し続けるので、新しい版を誤って読み込むことはない。新しい版を使うには、利用側を新しい版に対して再ビルドする。Windows では DLL のファイル名が変わらないので、利用側の再ビルドと、DLL を一緒に置き換えることが必要である。

patch の版と、1.0.0 以降の minor の版では、互換を壊す変更を入れない。
