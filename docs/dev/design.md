# 設計の考え方（保守者向け）

この文書は、CLOpts の構成と名前を決めるときの考え方を、理由とともに示す。ファイルや関数を足すとき、動かすとき、名前を付けるときに、この文書で判断する。構成そのもの（モジュールの一覧、宣言モデル、解析の流れ）は [アーキテクチャ](architecture.md) にある。

コードがこの文書に合っていない箇所と、それを直す作業は、リポジトリ直下の `TODO.md` にある。

## 1. 名前は概念に付ける

関数と型の名前には、それが表す概念の名前を入れる。モジュール（`src/` のディレクトリ）の名前は入れない。

- モジュールの名前は「どこにあるか」を表す。それはパスが示している。名前が示すのは「何であるか」である。
- 概念の名前だけで成り立つ名前は、概念が整理できている証拠になる。`clopts_option_t` にモジュールの名前が要らないのは、オプションという概念が 1 つで、ほかの何ともぶつからないからである。

### 名前がぶつかるのは、分け方を見直す合図である

モジュールの名前を外すと名前がぶつかる、あるいは意味が通らなくなるときは、接頭辞を足して避けない。概念の分け方を見直す。

| 兆候 | 原因 | 直し方 |
|------|------|--------|
| 内部の関数と公開の関数が、同じ `clopts_result_get_positional_count` になる | 解析の途中の記録と、利用者に返す結果を、1 つの型が兼ねている | 途中の記録（`matches`）と、できあがった結果（`result`）に分ける |
| `clopts_result_get_error_command`、`clopts_result_get_error_option` のように、型でない語（`error_`）が並ぶ | 名前のない概念（使い方エラー）が接頭辞になっている | 型（`clopts_usage_error_t`）にして、関数をその型に付ける |
| `clopts_parse` と `clopts_parse_with_env` を別のモジュールに置きたくなる | 1 つの概念を 2 か所に分けようとしている | 同じファイルに置けるように、依存の向きを決め直す |

## 2. 1 つの概念に、ヘッダとソースと接頭辞を 1 組

1. `src/<モジュール>/x.h` で宣言する関数と型は、`clopts_x` か `clopts_x_*` と名付け、同じディレクトリの `x.c` で定義する。
2. OS ごとの実装は `x_win32.c` と `x_posix.c` に置く。宣言は `x.h` のままである。
3. 何でも入れるヘッダ（`<モジュール>_internal.h`、`util.h`）は置かない。内部ヘッダは概念ごとに 1 つである。
4. `static` 関数には、`clopts_` も概念の名前も付けなくてよい。

目的は、名前から置き場所が決まることである。`clopts_vec_push` は `vec.h` が宣言し、`vec.c` が定義する。

何でも入れるヘッダを置かないのは、include から依存が読めなくなるからである。`decl/scope.h` を include していれば Scope を使っていると分かるが、`decl/decl_internal.h` では、宣言のどの部分に頼っているのかが分からない。概念の境目も育たない。

### 公開か内部かは、名前では区別しない

公開か内部かは、宣言するヘッダの場所（`include/clopts/` か `src/`）と `abi/clopts.symbols` で決まる。同じ概念なら、公開の関数と内部の関数が同じ接頭辞を持つ（公開の `clopts_argv_create` と、内部の `clopts_argv_sentinel`）。

内部用の接頭辞を足すと、同じ概念に名前が 2 つできる。関数を公開にするとき、内部に戻すときに、改名も要る。

### 公開の関数の名前

- 型 `clopts_x_t` の関数は `clopts_x_<動詞>` とする（`clopts_option_create`、`clopts_result_get_value`）。
- 型に属さない操作は、動詞で始める（`clopts_parse`、`clopts_write_help`、`clopts_set_allocator`）。ヘッダは動詞か対象の名前にする（`parse.h`、`write.h`、`allocator.h`）。

## 3. src、include、tests を同じ形にする

```
src/<モジュール>/x.c               定義
src/<モジュール>/x.h               内部の宣言（構造体の中身と、内部の関数）
include/clopts/<モジュール>/x.h    公開の宣言
tests/<モジュール>/test_x.c        テスト
```

1. 公開ヘッダ `clopts/<モジュール>/x.h` が宣言する関数は、`src/<モジュール>/x.c`（OS ごとなら `x_win32.c` と `x_posix.c`）が定義する。
2. 内部ヘッダ `src/<モジュール>/x.h` は、同じ名前の公開ヘッダを include し、構造体の中身と内部の関数を足す。
3. 不透明な型 `clopts_x_t` は、`x.h` が前方宣言する。型の前方宣言だけを集めたヘッダは置かない。
4. 公開ヘッダは、単独で include できる。使う型のヘッダは、自分で include する。
5. マクロや型だけで、関数を宣言しない公開ヘッダは、`.c` を持たなくてよい。それでも、モジュールのディレクトリに置く。`CLOPTS_API` を決める `export.h` は、どのモジュールも使うので、いちばん下のモジュールに置く。
6. モジュールに属さない公開ヘッダは、全部入りの `clopts.h` だけである。

理由は 3 つある。

- 公開の関数の宣言と定義が、同じパスで引ける。
- 公開ヘッダどうしの include も、モジュールの依存の向き（4 章）に従う。向きを機械的に検査できる。
- 公開ヘッダと `.c` が 1 対 1 にならないときに、すぐ分かる。1 対 1 にならないのは、概念の分け方か、置くモジュールが違っている合図である。

利用者はふつう `clopts/clopts.h` だけを include する。ディレクトリの名前が利用者のコードに現れるのは、ヘッダを選んで include するときだけである。

## 4. ディレクトリは依存の向きを表す

モジュールを分ける基準は、何に依存してよいかである。モジュールは名前空間ではない。

1. **ドメインを知らない部品は、いちばん下に置く。** 確保、サイズの計算、可変長配列、UTF-8 の読み取りは、オプションもコマンドも知らない。
2. **OS に触るコードは 1 つのモジュールに集め、`*_win32.c` と `*_posix.c` に閉じ込める。** ほかのモジュールは、OS を知らないヘッダ越しにそれを使う。OS に触らずに書ける部分（コマンドラインの分割）は別のファイルにして、どの OS でもテストする。
3. **宣言は解析を知らない。解析は文面を知らない。**
4. **外側のモジュールは、公開ヘッダだけで中心を読む。** 文面のモジュールは、宣言と結果を公開の読み取り関数だけで読む。ライブラリの利用者が書けることしかしない。
5. **ファイルごとの例外は置かない。** 規則は「モジュール A はモジュール B を include できる」の形だけにする。

4 の裏返しとして、外側のモジュールが内部ヘッダを欲しがったら、公開 API に足りないものがある。文面が「コマンドの名前に隠れるグローバルオプション」を公開 API だけで判定しようとして、名前の照合の規則を書き直すことになるなら、足りないのは隠す判定の公開関数である。

5 の裏返しとして、例外が要るなら、置き場所が違っている。

依存の向きは、テスト（ラベル `structure`）で検査する。モジュールを足すとき、依存を変えるときは、検査の規則も同じ変更で直す。

## 5. 1 つの規則は 1 か所に書く

同じ規則が 2 か所に要るようになったら、書き写さない。その規則の持ち主である概念に関数を置き、両方から呼ぶ。

| 規則 | 持ち主 |
|------|--------|
| 書かれた名前がどのオプションを指すか（完全一致、次に `--no-<name>`。選ばれたコマンド、次にプログラム） | 宣言（Scope の中の照合と、Scope をまたぐ検索） |
| UTF-8 の並びの読み方（最短形、サロゲート、上限） | ドメインを知らない部品 |
| argv の 1 要素の形（`--`、`--name=value`、`-abc`） | 解析の字句の読み取り |

- 持ち主は、その規則を使うモジュールすべてが依存できる、いちばん上のモジュールに置く。
- 外側のモジュールが使うなら、公開の関数にする。
- 同じデータを読む経路も 1 本にする。公開の読み取り関数と、同じことをする内部の関数を、並べて持たない。

## 6. 作る途中のものと、できあがったものを分ける

1. できあがったものは、作ってから変えない。受け取る側には `const` で渡す。
2. 作る途中の状態は、別の型にする。できあがったものは、それを受け取って一度だけ作る。
3. できあがったものに「あとから設定する関数」（`set_error`、`finish`）が要るなら、途中の状態が混ざっている。

解析の結果は、利用者が読むだけの値である。解析が argv を読みながら書き足していく記録とは、別の型にする。宣言も同じで、組み立てている間はビルダー関数で書き、プログラムに渡した後は読むだけである。

### 同じに扱えるものだけを、共通の型にする

読むときと書くときで、共通にできる範囲が違うことがある。プログラムとコマンドは、どちらも「オプションと位置引数の並び」（Scope）を持ち、読み方は同じである。足すときの規則は持ち主ごとに違う（プログラムは、サブコマンドがあると位置引数を持てない）。

このときは、読み取りだけを共通の型（Scope）の関数にし、足す関数は持ち主に残す。足す関数まで共通の型に寄せると、持ち主ごとの規則を共通の型が知ることになる。

## 7. src に置かないもの

- **テストだけが使う経路。** テストのために本体に入口を足さない。テストは、公開 API か、本体も使っている内部の関数を呼ぶ。
- **互換のための別名、移行用の関数、古い名前。** `AGENTS.md` のとおりである。
- **利用者が公開 API で短く書けること。** ヘルプ用のオプションを作る関数を置かないのと同じである（[アーキテクチャ](architecture.md)の「設計の判断」）。

## 8. 迷ったときの問い

1. これは何という概念か。1 語で言えるか。言えないなら、2 つのものが混ざっていないか。
2. その名前のファイルは、もうあるか。あればそこに置く。なければ `x.c` と `x.h` を作る。
3. モジュールの名前を外しても、名前はぶつからないか。ぶつかるなら、概念を分け直す。
4. 何に依存するか。OS に触るか。宣言を知るか。結果を知るか。置くモジュールは、それで決まる。
5. 同じ規則を、別の場所にもう書いていないか。
6. 公開の関数なら、ヘッダと同じ名前の `.c` で定義できるか。できないなら、置くモジュールか名前が違う。
7. 規則に例外を足そうとしていないか。

## 9. 採らなかった案

| 案 | 採らなかった理由 |
|----|------------------|
| 内部の関数にモジュールの名前を付ける（`clopts_core_*`、`clopts_parser_*`） | 1 章のとおり。概念の分け方の問題を、接頭辞が隠す |
| 公開ヘッダを平置きにする（`include/clopts/*.h`） | 公開ヘッダと `.c` の対応が、パスから読めない。公開ヘッダどうしの依存の向きを検査できない |
| 型の前方宣言を集めたヘッダ（`types.h`） | 型の宣言が、その型のヘッダにない。公開ヘッダの include に循環はないので、要らない |
| モジュールごとの全部入りヘッダ（`decl.h`） | `clopts/decl/program.h` が宣言のヘッダをすべて include する。全部入りは `clopts.h` の 1 つで足りる |
| `src/` を平置きにする | この規模なら可能だが、依存の向きを機械的に検査するために、ディレクトリを使う |
| 層をまたぐ関数を置く `src/clopts.c` | どのモジュールにも属さないファイルは、依存の規則の外になる |
| OS のモジュールを公開 API の上に置き、`clopts_parse` をそこで定義する | 解析は OS のモジュールに依存しなくなるが、`clopts_parse` と `clopts_parse_with_env` が別のモジュールに分かれる。公開ヘッダも 2 つに分かれる。どちらかを改名すると、いちばん使う入口の名前が長くなる |
| OS ごとに 1 ファイルにする（`win32.c`、`posix.c`） | 接頭辞からファイルが決まらない。`clopts_argv_create` の定義が、名前から引けない |
| Scope に足す操作も公開する（`clopts_scope_add_option`） | 6 章のとおり。組み立て用（非 `const`）と読み取り用（`const`）で、Scope を得る関数も 2 つ要る |
| 名前からオプションを引く、汎用の公開関数 | `--no-<name>` の形の名前を、確保なしでは渡せない。外側のモジュールに要るのは、隠す判定だけである |
| プログラム自身の範囲を Command で表す、コマンドを入れ子にする | [アーキテクチャ](architecture.md)の「設計の判断」のとおり |

## 10. 参考にした設計

| ライブラリ | 取り入れた点 |
|------------|--------------|
| Lua | 概念ごとに `.c`、`.h`、接頭辞を 1 組にする（`ltable.c`、`ltable.h`、`luaH_`）。補助ライブラリ `lauxlib` は、公開 API だけで書く（文面のモジュール） |
| LLVM | 公開ヘッダとソースを、同じ形のディレクトリに置く（`include/llvm/Support/` と `lib/Support/`） |
| SQLite | 中心は OS の関数を呼ばない。OS ごとの実装を、OS を知らないヘッダ越しに使う（`os.h` と、`os_unix.c`、`os_win.c`） |
| clap（Rust） | 宣言、解析、出力の分け方。字句の読み取りを別の部品にする（`clap_lex`）。解析が記録するもの（`ArgMatches`）と、解析の結果を分ける |
| glibc argp | 解析、ヘルプ、整形つきの出力先（`argp-fmtstream`）を分ける |
