# 設計の考え方（保守者向け）

この文書は、CLOpts の構成と名前を決めるときの考え方を、理由とともに示す。ファイルや関数を足すとき、動かすとき、名前を付けるときに、この文書で判断する。構成そのもの（モジュールの一覧、宣言モデル、解析の流れ）は [アーキテクチャ](architecture.md) にある。

## 1. 名前は概念に付ける

関数と型の名前には、それが表す概念の名前を入れる。モジュール（`src/` のディレクトリ）の名前は入れない。

- モジュールの名前は「どこにあるか」を表す。それはパスが示している。名前が示すのは「何であるか」である。
- 概念の名前だけで成り立つ名前は、概念が整理できている証拠になる。`clopts_option_t` にモジュールの名前が要らないのは、オプションという概念が 1 つで、ほかの何ともぶつからないからである。

### 名前がぶつかるのは、分け方を見直す合図である

モジュールの名前を外すと名前がぶつかる、あるいは意味が通らなくなるときは、接頭辞を足して避けない。概念の分け方を見直す。

| 兆候 | 原因 | 直し方 |
|------|------|--------|
| 内部の関数と公開の関数が、同じ `clopts_result_get_positional_count` になる | 解析の途中の記録と、利用者に返す結果を、1 つの型が兼ねている | 途中の記録（`matches`）と、できあがった結果（`result`）に分ける |
| `clopts_result_get_error_command`、`clopts_result_get_error_option` のように、型でない語（`error_`）が並ぶ | 名前のない概念（使い方エラー）が接頭辞になっている | 型（`clopts_usage_error_t`）にして、関数をその型に付ける |
| `clopts_parse` と `clopts_parse_with_env` を別のモジュールに置きたくなる | 1 つの概念を 2 か所に分けようとしている | 同じファイルに置けるように、依存の向きを決め直す |

## 2. 1 つの概念に、ヘッダとソースを 1 組

1. 概念 x の関数と型は、`src/<モジュール>/x.h` で宣言し、同じディレクトリの `x.c` で定義する。
2. OS ごとの実装は `x_win32.c` と `x_posix.c` に置く。宣言は `x.h` のままである。
3. 何でも入れるヘッダ（`<モジュール>_internal.h`、`util.h`）は置かない。内部ヘッダは概念ごとに 1 つである。x の実装を見せる必要があるときだけ、実装ヘッダ `x_impl.h` をもう 1 つ置く（3 章「内部ヘッダの種類」）。
4. `static` 関数には、`clopts_` も概念の名前も付けなくてよい。

目的は、概念の名前から置き場所が決まることである。可変長配列は `vec.h` が宣言し、`vec.c` が定義する。関数の名前のどこまでを置き場所に縛るかは、次の「名前の付け方」で決める。

`<モジュール>_internal.h` を置かないことは、テスト `structure.names`（`tests/structure/check_names.cmake`）で検査する。どのヘッダにも宣言のない定義（`static` を除く）は、コンパイラが `-Wmissing-prototypes` で見つける。宣言と定義が同じ名前のファイルにあることは、レビューで確かめる。

何でも入れるヘッダを置かないのは、include から依存が読めなくなるからである。`decl/scope.h` を include していれば Scope を使っていると分かるが、`decl/decl_internal.h` では、宣言のどの部分に頼っているのかが分からない。概念の境目も育たない。

### 公開か内部かは、名前では区別しない

公開か内部かは、宣言するヘッダの場所（`include/clopts/` か `src/`）と `abi/clopts.symbols` で決まる。同じ型なら、公開の操作と内部の操作が同じ接頭辞を持つ（公開の `clopts_argv_create` と、内部の `clopts_argv_sentinel`）。

内部用の接頭辞を足すと、同じ概念に名前が 2 つできる。関数を公開にするとき、内部に戻すときに、改名も要る。

### 名前の付け方

名前は、公開でも内部でも、どれも `clopts_` / `CLOPTS_` で始めて、ライブラリの名前空間に入れる。その中で、ヘッダの名前で縛るのは、型とその操作の組だけである。この規則は公開と内部で同じである。

| 種類 | 例 | 名前の付け方 |
|------|----|--------------|
| 型とその操作 | `clopts_result_t`、`clopts_result_get_status`、`clopts_option_create`、内部の `clopts_vec_t`、`clopts_vec_push` | 型 `clopts_x_t` は `x.h` が宣言し、操作は `clopts_x_<動詞>` として、型と同じヘッダ（実装ヘッダ `x_impl.h` を含む）で宣言する |
| 型に属さない関数 | `clopts_parse`、`clopts_write_help`、`clopts_set_allocator`、`clopts_file_write`、内部の `clopts_malloc`、`clopts_strdup`、`clopts_utf8_valid` | 何をするかで付ける |
| ライブラリ全体の印 | `CLOPTS_API` | 役割で付ける |
| 引数のフラグ | `CLOPTS_PREFIX_PROGRAM` | 引数の意味で付ける |
| 語彙としての列挙 | `clopts_parse_status_t`、`clopts_source_t` | 表す意味で付ける |
| 利用者が埋めて渡すデータの型 | `clopts_allocator_t` | 中身で付ける |
| コールバックの型 | `clopts_write_fn`、`clopts_env_fn` | コールバックの役割（何をするか）の名前に `_fn` を付ける |

- 型とその操作をヘッダの名前で縛るのは、オブジェクトとその操作を 1 組にして、名前から置き場所が引けるようにするためである。`clopts_result_get_status` を見れば、`result.h` の型の操作だと分かる。
- それ以外を縛らないのは、名前は語彙であり、置き場所の手がかりではないからである。利用者はふつう `clopts/clopts.h` だけを include する。`CLOPTS_API` はどのヘッダで定義されてもよく、`clopts_parse_status_t` を「`result.h` にあるから」と `clopts_result_status_t` に変えても、意味の説明にはならない。`clopts_parse` と `clopts_write_help` がヘッダの名前（`parse.h`、`write.h`）と一致しているのは、意味で付けた結果である。
- 内部でも同じである。`clopts_malloc` と `clopts_strdup` は、標準の `malloc` と `strdup` の代わりだと名前から分かる。`memory.h` にあるからと `clopts_memory_alloc` と付けると、置き場所は分かるが、何の代わりかが名前から薄れる。置き場所は、呼ぶ側の include が示す。何でも入れるヘッダを置かないので、include は概念を 1 つ名指す。`clopts_utf8_valid` と `clopts_size_mul` がヘッダの名前と一致しているのは、`clopts_parse` と同じく、意味で付けた結果である。
- 公開ヘッダの置き場所は、名前ではなく、定義の置き場所で決める（3 章の 1）。
- 同じ値を 2 つの型から読めるようにしない。使い方エラーの起きたコマンドは、結果の選ばれたコマンドと同じなので、`clopts_result_get_command` だけで読む。

型の操作が型と同じヘッダにあることは、公開と内部の両方について、テスト `structure.names` で検査する。`clopts_x` か `clopts_x_*` という名前の関数は、型 `clopts_x_t` があれば、その型を宣言するヘッダ（`x_impl.h` は `x.h` とみなす）で宣言する。当てはまる型が 2 つあるときは、長いほうの型の操作とみなす（`clopts_usage_error_kind_t` と `clopts_usage_error_t`）。型に属さない関数の名前は検査しない。

## 3. src、include、tests を同じ形にする

```
src/<モジュール>/x.c               定義
src/<モジュール>/x.h               内部の宣言（構造体の中身と、内部の関数）
include/clopts/<モジュール>/x.h    公開の宣言
tests/<モジュール>/test_x.c        テスト
```

1. 公開ヘッダ `clopts/<モジュール>/x.h` が宣言する関数は、`src/<モジュール>/x.c`（OS ごとなら `x_win32.c` と `x_posix.c`）が定義する。
2. 内部ヘッダ `src/<モジュール>/x.h` は、同じ名前の公開ヘッダを最初に include し、`x.h` を使う側が要る構造体の中身と内部の関数を足す。埋め込む側や実装する側だけが要るものは、実装ヘッダ `x_impl.h` に置く（「内部ヘッダの種類」）。
3. 不透明な型 `clopts_x_t` は、`x.h` が前方宣言する。型の前方宣言だけを集めたヘッダは置かない。
4. 公開ヘッダは、単独で include できる。使う型のヘッダは、自分で include する。
5. マクロや型だけで、関数を宣言しない公開ヘッダは、`.c` を持たなくてよい。それでも、モジュールのディレクトリに置く。`CLOPTS_API` を決める `export.h` は、どのモジュールも使うので、いちばん下のモジュールに置く。
6. モジュールに属さない公開ヘッダは、全部入りの `clopts.h` だけである。

理由は 3 つある。

- 公開の関数の宣言と定義が、同じパスで引ける。
- 公開ヘッダどうしの include も、モジュールの依存の向き（4 章）に従う。向きを機械的に検査できる。
- 公開ヘッダと `.c` が 1 対 1 にならないときに、すぐ分かる。1 対 1 にならないのは、概念の分け方か、置くモジュールが違っている合図である。

利用者はふつう `clopts/clopts.h` だけを include する。ディレクトリの名前が利用者のコードに現れるのは、ヘッダを選んで include するときだけである。

### 内部ヘッダの種類

内部ヘッダは、誰に見せるかで分ける。

| 種類 | 誰が使うか | 置き場所 |
|------|------------|----------|
| 公開 | 利用者 | `include/clopts/<モジュール>/x.h` |
| 内部 | ライブラリのほかの概念（ほかのモジュールなら、依存してよいモジュールのものだけ） | `src/<モジュール>/x.h` |
| 実装 | x を埋め込む概念と、x の OS ごとの実装 | `src/<モジュール>/x_impl.h` |
| ファイルの中だけ | 1 つのファイル | `.c` の中（`static`、構造体の定義） |

1. 既定は `.c` に閉じる。構造体は `.c` で定義して不透明な型にし、補助関数は `static` にする。
2. 実装ヘッダ `x_impl.h` は、継承に当たる場面でだけ置く。ほかの型が x を値として埋め込む（program と command が Scope を埋め込む）ときと、x の実装が OS ごとのファイルに分かれる（`argv_posix.c` と `argv_win32.c`）ときである。どちらも、使う側が x の中身を知らなければ書けない。
3. `x_impl.h` は概念 x のものである。型 x の操作は `clopts_x_*` と名付け、`x.c` か `x_<os>.c` で定義する。`x.h` と `x_impl.h` の間で関数を動かしても、改名は要らない。
4. `x_impl.h` は、最初に概念 x のヘッダ（内部の `x.h`、なければ公開の `x.h`）を include する。同じモジュールのファイルしか include できない。
5. テストは、どの種類の内部ヘッダも include してよい。

`_impl` は、見え方の段階を名前にしたものではない。避けているのは、同じ関数を公開と内部で別の名前にすること（`_internal_`）である。`_impl` が表すのは、ヘッダの役割、つまり「x の実装を見せる面」である。

### 構造体の中身の見せ方

分ける基準は、不変条件の有無ではなく、x を使う側のうち誰が中身を知る必要があるかである。

| 種類 | 基準 | 置き場所 | 例 |
|------|------|----------|----|
| 値の型 | `x.h` を使う側が、値として持つ（スタックに置く、配列にする、埋め込む）か、フィールドを読む | `x.h` | `clopts_vec_t`、`clopts_slot_t`、`clopts_token_t`、`clopts_lookup_t`、`clopts_out_t`、`clopts_env_t`、内部の `clopts_usage_error_t` |
| ハンドル | 中身を知る必要があるのは、x を作るファイルだけである | `x.c` | program、command、option、positional、matches、result |
| 継承される型 | 中身を知る必要があるのは、x を埋め込む側と x を OS ごとに実装する側だけで、`x.h` を使うほかの側は知らなくてよい | `x_impl.h` | `clopts_scope_t`（program と command が埋め込む。`lookup.c` は名前を引くだけ）、`struct clopts_argv` |

中身を見せた型にも、不変条件があってよい（`clopts_vec_t` の `len <= cap`、`clopts_slot_t` の `value == owned`）。そのときは、フィールドを読むのは自由で、書くのは `clopts_x_*` の関数を通すだけ、と型の説明に書く。`clopts_lookup_t`、`clopts_token_t`、内部の `clopts_usage_error_t` のように、不変条件がなく、使う側が直接書いてよい型もある。

公開の構造体は、この基準に加えて「その形で ABI を凍結してよいか」で決める（[ABI の互換性](../abi.md)）。公開で中身を出すのは、利用者が埋めて渡す `clopts_allocator_t` だけである。同じ型でも見せる相手で扱いが変わり、`clopts_usage_error_t` は内部では値の型、公開では不透明な型である。

### 公開ヘッダと同じ名前の内部ヘッダ

`src/decl/scope.h` と `clopts/decl/scope.h` のように、内部ヘッダが公開ヘッダと同じ名前になることがある。1 つの概念の、利用者に見せる面と内部の面だからである。内部ヘッダは、最初にその公開ヘッダを include する。

- 区別はパスが担う。`"decl/scope.h"` は `src/` の下にしかなく、`"clopts/decl/scope.h"` は `include/` の下にしかない。
- インクルードガードも別にする（`CLOPTS_DECL_SCOPE_H` と `CLOPTS_SRC_DECL_SCOPE_H`）。
- 内部ヘッダの名前を変える（`scope_internal.h`）と、見え方の段階を名前にすることになる。

代償は、エディタの検索などで同じ名前の候補が 2 つ出ることである。

実装ヘッダの操作が型と組になっていることは `structure.names` で、実装ヘッダをほかのモジュールから include しないことは `structure.modules` で検査する。最初の include は、レビューで確かめる。

## 4. ディレクトリは依存の向きを表す

モジュールを分ける基準は、何に依存してよいかである。モジュールは名前空間ではない。

1. **ドメインを知らない部品は、いちばん下に置く。** 確保、サイズの計算、可変長配列、UTF-8 の読み取り、エラーの種類（不正な名前、重なり、衝突など）は、オプションもコマンドも知らない。
2. **OS に触るコードは 1 つのモジュールに集め、`*_win32.c` と `*_posix.c` に閉じ込める。** ほかのモジュールは、OS を知らないヘッダ越しにそれを使う。OS に触らずに書ける部分（コマンドラインの分割）は別のファイルにして、どの OS でもテストする。
3. **宣言は解析を知らない。解析は文面を知らない。**
4. **外側のモジュールは、公開ヘッダだけで中心を読む。** 文面のモジュールは、宣言と結果を公開の読み取り関数だけで読む。ライブラリの利用者が書けることしかしない。
5. **ファイルごとの例外は置かない。** 規則は「モジュール A はモジュール B を include できる」の形だけにする。

4 の裏返しとして、外側のモジュールが内部ヘッダを欲しがったら、公開 API に足りないものがある。文面が「コマンドの名前に隠れるグローバルオプション」を公開 API だけで判定しようとして、名前の照合の規則を書き直すことになるなら、足りないのは隠す判定の公開関数である。

5 の裏返しとして、例外が要るなら、置き場所が違っている。

依存してよいモジュールの内部ヘッダは include できる。ただし、実装ヘッダ（3 章「内部ヘッダの種類」）には触れない。

依存の向きは、テスト `structure.modules`（`tests/structure/check_structure.cmake`）で、`src/` と `include/clopts/` の両方について検査する。モジュールを足すとき、依存を変えるときは、検査の規則も同じ変更で直す。

## 5. 1 つの規則は 1 か所に書く

同じ規則が 2 か所に要るようになったら、書き写さない。その規則の持ち主である概念に関数を置き、両方から呼ぶ。

| 規則 | 持ち主 |
|------|--------|
| 書かれた名前がどのオプションを指すか（完全一致、次に `--no-<name>`。選ばれたコマンド、次にプログラム） | 宣言（Scope の中の照合と、Scope をまたぐ検索） |
| UTF-8 の並びの読み方（最短形、サロゲート、上限） | ドメインを知らない部品 |
| argv の 1 要素の形（`--`、`--name=value`、`-abc`） | 解析の字句の読み取り |

- 持ち主は、その規則を使うモジュールすべてが依存できる、いちばん上のモジュールに置く。
- 外側のモジュールが使うなら、公開の関数にする。
- 同じデータを読む経路も 1 本にする。公開の読み取り関数と、同じことをする内部の関数を、並べて持たない。

## 6. 作る途中のものと、できあがったものを分ける

1. できあがったものは、作ってから変えない。受け取る側には `const` で渡す。
2. 作る途中の状態は、別の型にする。できあがったものは、それを受け取って一度だけ作る。
3. できあがったものに「あとから設定する関数」（`set_error`、`finish`）が要るなら、途中の状態が混ざっている。

解析の結果は、利用者が読むだけの値である。解析が argv を読みながら書き足していく記録とは、別の型にする。宣言も同じで、組み立てている間はビルダー関数で書き、プログラムに渡した後は読むだけである。

### 同じに扱えるものだけを、共通の型にする

読むときと書くときで、共通にできる範囲が違うことがある。プログラムとコマンドは、どちらも「オプションと位置引数の並び」（Scope）を持ち、読み方は同じである。足すときの規則は持ち主ごとに違う（プログラムは、サブコマンドがあると位置引数を持てない）。

このときは、読み取りだけを共通の型（Scope）の関数にし、足す関数は持ち主に残す。足す関数まで共通の型に寄せると、持ち主ごとの規則を共通の型が知ることになる。

## 7. エラーの種類は、ドメインを知らない語彙にする

ビルダー関数が返すエラー（`clopts_error_t`）は、errno の `EINVAL`、`EEXIST`、`ENOMEM` と同じく、何が起きたかの種類だけを表す。どの規則が破れたかは表さない。

1. 列挙子には、オプションやコマンドの語彙を入れない（`DUPLICATE`。`DUPLICATE_OPTION` にしない）。どの呼び出しがどの種類を返すかは、呼び出す側のモジュールが決める。
2. 種類を足すのは、今の種類のどれにも当てはまらないときだけである。新しい規則を足したら、まず今の種類（`NOT_APPLICABLE`、`CONFLICT`、`ORDER` など）に入れる。
3. 細かい理由を返すしくみ（どの属性とぶつかったか、などのデバッグ用の文）は置かない。要るようになってから考える。

理由は 3 つある。

- **エラーの型を base に置ける。** 語彙がドメインを知らなければ、エラーの型はいちばん下のモジュールの部品になり、4 章の 1 と矛盾しない。宣言の規則ごとの列挙子は、base にオプションの知識を持ち込む。
- **宣言エラーは、プログラマの誤りである。** 開発中に一度出て、直せば二度と出ない。失敗した呼び出しの場所は分かっているので、種類が分かれば原因にたどり着ける。利用者が実行時に種類で分岐することは、まずない。
- **規則を足しても、公開の列挙が増えない。** 規則ごとに列挙子を足すと、宣言の規則を変えるたびに公開 API と ABI が変わる。

## 8. src に置かないもの

- **テストだけが使う経路。** テストのために本体に入口を足さない。テストは、公開 API か、本体も使っている内部の関数を呼ぶ。
- **互換のための別名、移行用の関数、古い名前。** `AGENTS.md` のとおりである。
- **利用者が公開 API で短く書けること。** ヘルプ用のオプションを作る関数を置かないのと同じである（[アーキテクチャ](architecture.md)の「設計の判断」）。

## 9. 迷ったときの問い

1. これは何という概念か。1 語で言えるか。言えないなら、2 つのものが混ざっていないか。
2. その名前のファイルは、もうあるか。あればそこに置く。なければ `x.c` と `x.h` を作る。
3. モジュールの名前を外しても、名前はぶつからないか。ぶつかるなら、概念を分け直す。
4. 何に依存するか。OS に触るか。宣言を知るか。結果を知るか。置くモジュールは、それで決まる。
5. 同じ規則を、別の場所にもう書いていないか。
6. 公開の関数なら、ヘッダと同じ名前の `.c` で定義できるか。できないなら、置くモジュールか名前が違う。
7. 規則に例外を足そうとしていないか。
8. 例外をなくすために、規則をその根拠の外まで広げていないか。
9. エラーの種類を足すなら、今の種類のどれにも当てはまらないか。列挙子にドメインの語が入っていないか。

## 10. 採らなかった案

| 案 | 採らなかった理由 |
|----|------------------|
| 内部の関数にモジュールの名前を付ける（`clopts_core_*`、`clopts_parser_*`） | 1 章のとおり。概念の分け方の問題を、接頭辞が隠す |
| 公開ヘッダの内部版を `x_internal.h` と名付ける | 見え方の段階が名前になる。同じ概念に名前が 2 つでき、関数を公開と内部の間で動かすときに include も直すことになる |
| 名前をすべてヘッダの名前で始める（`export.h` を `api.h` に、`clopts_parse_status_t` を `clopts_result_status_t` に、`clopts_set_allocator` を `clopts_memory_set_allocator` に、内部の `clopts_malloc` を `clopts_memory_alloc` に） | 2 章「名前の付け方」のとおり。型に属さない名前は、置き場所を名前から引く必要がない。置き場所は include が示す。例外をなくすことが目的になり、意味で付けた名前を崩す |
| ほかのモジュールに見せる内部ヘッダを列挙する | モジュールの依存の向きの規則と二重になる。実装を見せる面だけは、実装ヘッダとして同じモジュールに閉じる |
| 内部の全部入りヘッダ（SQLite の `sqliteInt.h`） | 2 章のとおり。include から依存が読めない |
| 公開ヘッダを平置きにする（`include/clopts/*.h`） | 公開ヘッダと `.c` の対応が、パスから読めない。公開ヘッダどうしの依存の向きを検査できない |
| 型の前方宣言を集めたヘッダ（`types.h`） | 型の宣言が、その型のヘッダにない。公開ヘッダの include に循環はないので、要らない |
| モジュールごとの全部入りヘッダ（`decl.h`） | `clopts/decl/program.h` が宣言のヘッダをすべて include する。全部入りは `clopts.h` の 1 つで足りる |
| `src/` を平置きにする | この規模なら可能だが、依存の向きを機械的に検査するために、ディレクトリを使う |
| 層をまたぐ関数を置く `src/clopts.c` | どのモジュールにも属さないファイルは、依存の規則の外になる |
| OS のモジュールを公開 API の上に置き、`clopts_parse` をそこで定義する | 解析は OS のモジュールに依存しなくなるが、`clopts_parse` と `clopts_parse_with_env` が別のモジュールに分かれる。公開ヘッダも 2 つに分かれる。どちらかを改名すると、いちばん使う入口の名前が長くなる |
| OS ごとに 1 ファイルにする（`win32.c`、`posix.c`） | 接頭辞からファイルが決まらない。`clopts_argv_create` の定義が、名前から引けない |
| Scope に足す操作も公開する（`clopts_scope_add_option`） | 6 章のとおり。組み立て用（非 `const`）と読み取り用（`const`）で、Scope を得る関数も 2 つ要る |
| 名前からオプションを引く、汎用の公開関数 | `--no-<name>` の形の名前を、確保なしでは渡せない。外側のモジュールに要るのは、隠す判定だけである |
| プログラム自身の範囲を Command で表す、コマンドを入れ子にする | [アーキテクチャ](architecture.md)の「設計の判断」のとおり |
| 宣言の規則ごとのエラーの列挙子（`DUPLICATE_OPTION`、`NEGATION_CONFLICT`、`MIXED_LAYOUT` など）を、`clopts/decl/decl_error.h` に置く | 7 章のとおり。説明は細かくなるが、規則を足すたびに公開の列挙が増える。名前にモジュールの名前（`decl_`）が入り、1 章にも反する |
| エラーに細かい理由（どの属性とぶつかったか）を添える | 7 章の 3。宣言エラーは開発中に一度直せば済み、失敗した呼び出しと種類で原因にたどり着ける。要るようになってから考える |

## 11. 参考にした設計

| ライブラリ | 取り入れた点 |
|------------|--------------|
| Lua | 概念ごとに `.c`、`.h`、接頭辞を 1 組にする（`ltable.c`、`ltable.h`、`luaH_`）。CLOpts は、接頭辞で縛るのを型とその操作の組に絞る。補助ライブラリ `lauxlib` は、公開 API だけで書く（文面のモジュール） |
| LLVM | 公開ヘッダとソースを、同じ形のディレクトリに置く（`include/llvm/Support/` と `lib/Support/`）。表現を見せるヘッダを別にする（`LLVMContextImpl.h`、`AttributeImpl.h`）。これは公開ヘッダの内部版ではなく、オブジェクトの表現を見せる面で、実装ヘッダ `x_impl.h` の名前と役割はこれに倣う |
| libgit2 | 公開ヘッダと同じ名前の内部ヘッダが、公開ヘッダを include して構造体の中身と内部の関数を足す（`include/git2/repository.h` と `src/libgit2/repository.h`）。ただし libgit2 は内部の関数を `git_repository__*` と名前で区別し、CLOpts は区別しない |
| CPython | ヘッダを見せる相手で段に分ける（公開 API、CPython 固有の API、内部 API） |
| GLib / GObject | 実装を見せるヘッダを別にする（`*-private.h`） |
| SQLite | 中心は OS の関数を呼ばない。OS ごとの実装を、OS を知らないヘッダ越しに使う（`os.h` と、`os_unix.c`、`os_win.c`） |
| clap（Rust） | 宣言、解析、出力の分け方。字句の読み取りを別の部品にする（`clap_lex`）。解析が記録するもの（`ArgMatches`）と、解析の結果を分ける |
| glibc argp | 解析、ヘルプ、整形つきの出力先（`argp-fmtstream`）を分ける |
