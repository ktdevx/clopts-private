# 設計の考え方（保守者向け）

この文書は、CLOpts の構成と名前を決めるときの考え方を、理由とともに示す。ファイルや関数を足すとき、動かすとき、名前を付けるときに、この文書で判断する。構成そのもの（モジュールの一覧、宣言モデル、解析の流れ）は [アーキテクチャ](architecture.md) にある。

## 1. 名前は概念に付ける

概念をオブジェクト（構造体と、その値を主語にとる操作）として捉えられるときは、名前にその概念の名前を入れる（`clopts_x_t`、`clopts_x_<動詞>`）。捉えられないとき（働き、しくみ、語彙）は、何をするか、何を表すかで付ける（`clopts_parse`、`clopts_malloc`、`clopts_error_t`）。どちらの場合も、モジュール（`src/` のディレクトリ）の名前は入れない。付け方の詳しい規則は、2 章「名前の付け方」にある。

モジュールの名前を入れない理由は 3 つある。

- モジュールは依存の向きの単位で、名前空間ではない（4 章）。依存の向きを決め直すと、概念の置き場所が変わる。名前にモジュールの名前があると、そのたびに改名が要る。
- 公開か内部かを名前で区別しない（2 章）ので、モジュールの名前を付けると、利用者の見る名前に内部の構成が出る。
- 概念の分け方の問題を、接頭辞が隠す。次の節のとおりである。

### 名前がぶつかるのは、分け方を見直す合図である

モジュールの名前を外すと名前がぶつかる、あるいは意味が通らなくなるときは、接頭辞を足して避けない。概念の分け方を見直す。

| 兆候 | 原因 | 直し方 |
|------|------|--------|
| 内部の関数と公開の関数が、同じ `clopts_result_get_positional_count` になる | 解析の途中の記録と、利用者に返す結果を、1 つの型が兼ねている | 途中の記録（`matches`）と、できあがった結果（`result`）に分ける |
| `clopts_result_get_error_command`、`clopts_result_get_error_option` のように、型でない語（`error_`）が並ぶ | 名前のない概念（使い方エラー）が接頭辞になっている | 型（`clopts_usage_error_t`）にして、関数をその型に付ける |
| `clopts_parse` と `clopts_parse_with_env` を別のモジュールに置きたくなる | 1 つの概念を 2 か所に分けようとしている | 同じファイルに置けるように、依存の向きを決め直す |

## 2. 1 つの概念に、ヘッダとソースを 1 組

1. 概念 x の関数と型は、`src/<モジュール>/x.h` で宣言し、同じディレクトリの `x.c` で定義する。
2. OS ごとの実装は `x_win32.c` と `x_posix.c` に置く。宣言は `x.h` のままである。
3. 何でも入れるヘッダ（`<モジュール>_internal.h`、`util.h`）は置かない。内部ヘッダは概念ごとに 1 つで、見せる相手で分けない（3 章「内部ヘッダの種類」）。
4. `static` 関数には、`clopts_` も概念の名前も付けなくてよい。

目的は、概念の名前から置き場所が決まることである。可変長配列は `vec.h` が宣言し、`vec.c` が定義する。関数の名前のどこまでを置き場所に縛るかは、次の「名前の付け方」で決める。

`<モジュール>_internal.h` を置かないこと、公開ヘッダを持つ概念の内部ヘッダが `x_internal.h` であること（3 章「公開ヘッダを持つ概念の内部ヘッダ」）は、テスト `structure.names`（`tests/structure/check_names.cmake`）で検査する。どのヘッダにも宣言のない定義（`static` を除く）は、コンパイラが `-Wmissing-prototypes` で見つける。宣言と定義が同じ名前のファイルにあることは、レビューで確かめる。

何でも入れるヘッダを置かないのは、include から依存が読めなくなるからである。`decl/scope_internal.h` を include していれば Scope を使っていると分かるが、`decl/decl_internal.h` では、宣言のどの部分に頼っているのかが分からない。概念の境目も育たない。

### 公開か内部かは、名前では区別しない

公開か内部かは、宣言するヘッダの場所（`include/clopts/` か `src/`）と `abi/clopts.symbols` で決まる。同じ構造体なら、公開の操作と内部の操作が同じ接頭辞を持つ（公開の `clopts_argv_create` と、内部の `clopts_argv_sentinel`）。

内部用の接頭辞を足すと、同じ概念に名前が 2 つできる。関数を公開にするとき、内部に戻すときに、改名も要る。

### 名前の付け方

名前は、公開でも内部でも、どれも `clopts_` / `CLOPTS_` で始めて、ライブラリの名前空間に入れる。その中で、ヘッダの名前で縛るのは、構造体とその操作の組だけである。

| 種類 | 例 | 名前の付け方 |
|------|----|--------------|
| オブジェクト（構造体とその操作） | `clopts_result_t` と `clopts_result_get_status`、内部の `clopts_vec_t` と `clopts_vec_push` | 操作を持つ構造体 `clopts_x_t` は `x.h` が宣言し、操作は `clopts_x_<動詞>` として、構造体と同じヘッダ（内部ヘッダ `x_internal.h` を含む）で宣言する |
| それ以外 | 関数の `clopts_parse`、`clopts_malloc`、マクロの `CLOPTS_API`、フラグの `CLOPTS_PREFIX_PROGRAM`、列挙の `clopts_parse_status_t`、`clopts_error_t` と、その説明を返す `clopts_error_get_message`、利用者が埋めて渡す `clopts_allocator_t` | 何をするか、何を表すかで付ける |

コールバックの型は、その役割の名前に `_fn` を付ける（`clopts_write_fn`、`clopts_env_fn`）。

- 構造体とその操作をヘッダの名前で縛るのは、オブジェクトとその操作を 1 組にして、名前から置き場所が引けるようにするためである。`clopts_result_get_status` を見れば、`result.h` の構造体の操作だと分かる。
- それ以外を縛らないのは、名前は語彙であり、置き場所の手がかりではないからである。`CLOPTS_API` はどのヘッダで定義されてもよく、`clopts_parse_status_t` を「`result.h` にあるから」と `clopts_result_status_t` に変えても、意味の説明にはならない。
- 内部でも同じである。`clopts_malloc` と `clopts_strdup` は、標準の `malloc` と `strdup` の代わりだと名前から分かる。`alloc.h` にあるからと `clopts_alloc_block` と付けると、置き場所は分かるが、何の代わりかが名前から薄れる。置き場所は、呼ぶ側の include が示す。何でも入れるヘッダを置かないので、include は概念を 1 つ名指す。
- 縛らない名前がヘッダの名前と一致することはある（`parse.h` の `clopts_parse`、`error.h` の `clopts_error_get_message`、`utf8.h` の `clopts_utf8_valid`）。意味で付けた結果であり、規則ではない。

構造体の操作が構造体と同じヘッダにあることは、公開と内部の両方について、テスト `structure.names` で検査する。それ以外の名前は検査しない。

## 3. src と include を同じ形にする

```
src/<モジュール>/x.c               定義
src/<モジュール>/x.h               内部の宣言（構造体の中身と、内部の関数）
src/<モジュール>/x_internal.h      公開ヘッダを持つ概念の、内部の宣言（x.h の代わり）
include/clopts/<モジュール>/x.h    公開の宣言
tests/<モジュール>/                そのモジュールのテスト。ファイルは振る舞いごとに分けてよい
```

1. 公開ヘッダ `clopts/<モジュール>/x.h` が宣言する関数は、`src/<モジュール>/x.c`（OS ごとなら `x_win32.c` と `x_posix.c`）が定義する。
2. 公開ヘッダを持つ概念の内部ヘッダ `src/<モジュール>/x_internal.h` は、その公開ヘッダを最初に include し、構造体の中身と内部の関数を足す。
3. 不透明な型 `clopts_x_t` は、`x.h` が前方宣言する。型の前方宣言だけを集めたヘッダは置かない。
4. 公開ヘッダは、単独で include できる。使う型のヘッダは、自分で include する。
5. マクロや型だけで、関数を宣言しない公開ヘッダは、`.c` を持たなくてよい。それでも、モジュールのディレクトリに置く。`CLOPTS_API` を決める `export.h` は、どのモジュールも使うので、いちばん下のモジュールに置く。
6. モジュールに属さない公開ヘッダは、全部入りの `clopts.h` だけである。

理由は 3 つある。

- 公開の関数の宣言と定義が、同じパスで引ける。
- 公開ヘッダどうしの include も、モジュールの依存の向き（4 章）に従う。向きを機械的に検査できる。
- 公開ヘッダと `.c` が 1 対 1 にならないときに、すぐ分かる。1 対 1 にならないのは、概念の分け方か、置くモジュールが違っている合図である。

利用者はふつう `clopts/clopts.h` だけを include する。ディレクトリの名前が利用者のコードに現れるのは、ヘッダを選んで include するときだけである。

### 内部ヘッダの種類

宣言を見せる先は 3 段で、内部ヘッダは概念ごとに 1 つである。

| 種類 | 誰が使うか | 置き場所 |
|------|------------|----------|
| 公開 | 利用者 | `include/clopts/<モジュール>/x.h` |
| 内部 | ライブラリのほかのファイル（ほかのモジュールなら、依存してよいモジュールのものだけ） | `src/<モジュール>/x.h`（公開ヘッダを持つ概念なら `x_internal.h`） |
| ファイルの中だけ | 1 つのファイル | `.c` の中（`static`、構造体の定義） |

1. 既定は `.c` に閉じる。構造体は `.c` で定義して不透明な型にし、補助関数は `static` にする。
2. ほかのファイルが要るものは、内部ヘッダに置く。ほかの型が x を値として埋め込むとき（program と command が Scope を埋め込む）や、x の実装が OS ごとのファイルに分かれるとき（`argv_posix.c` と `argv_win32.c`）は、構造体の中身も内部ヘッダに置く。
3. 内部ヘッダを、見せる相手ごとに分けない。中身を見せる相手を絞るヘッダ（実装ヘッダ）は置かない。中身を書き換えてよい側は、型の説明で決める（「構造体の中身の見せ方」）。
4. テストは、どの内部ヘッダも include してよい。

`_internal` は、ヘッダのファイル名にだけ付ける。避けているのは、同じ関数を公開と内部で別の名前にすること（libgit2 の `git_repository__*` のような印）である。

### 構造体の中身の見せ方

分ける基準は、不変条件の有無ではなく、x を使う側のうち誰が中身を知る必要があるかである。

| 種類 | 基準 | 置き場所 | 例 |
|------|------|----------|----|
| 値の型 | x を使う側のどれかが、値として持つ（スタックに置く、配列にする、埋め込む）か、フィールドを読む。x を OS ごとのファイルで実装する | 内部ヘッダ | `clopts_vec_t`、`clopts_scope_t`（program と command が埋め込む）、`clopts_argv_t`（`argv_posix.c` と `argv_win32.c` が作る） |
| ハンドル | 中身を知る必要があるのは、x を作るファイルだけである | `x.c` | `clopts_program_t` |

中身を見せた型にも、不変条件があってよい（`clopts_vec_t` の `len <= cap`、`clopts_scope_t` の名前の重なりのなさ）。そのときは、フィールドを読むのは自由で、書くのは `clopts_x_*` の関数を通すだけ、と型の説明に書く。中身を見せる相手をヘッダで絞らないので、この説明とレビューが不変条件を守る。`clopts_token_t` のように、不変条件がなく、使う側が直接書いてよい型もある。

公開の構造体は、この基準に加えて「その形で ABI を凍結してよいか」で決める（[ABI の互換性](../abi.md)）。公開で中身を出すのは、利用者が埋めて渡す `clopts_allocator_t` だけである。同じ型でも見せる相手で扱いが変わり、`clopts_usage_error_t` は内部では値の型、公開では不透明な型である。

### 公開ヘッダを持つ概念の内部ヘッダ

公開ヘッダ `clopts/<モジュール>/x.h` を持つ概念の内部ヘッダは、`src/<モジュール>/x_internal.h` と名付ける（`clopts/decl/scope.h` と `decl/scope_internal.h`）。1 つの概念の、利用者に見せる面と内部の面である。内部ヘッダは、最初にその公開ヘッダを include する。

- ファイル名だけで、どちらの面か分かる。同じ名前にすると、エディタの検索やタブ、コンパイラのメッセージで 2 つが並び、パスまで読まないと区別できない。
- 公開ヘッダを持たない概念の内部ヘッダには、`_internal` を付けない（`vec.h`、`str.h`）。`src/` にあることで内部だと分かる。`_internal` は「公開の面もある」ことの印で、付くかどうかは公開ヘッダの有無だけで決まる。
- 概念を公開にする（公開ヘッダを足す）ときは、内部ヘッダを `x_internal.h` に改名する。公開をやめるときは `x.h` に戻す。関数を公開と内部の間で動かすときは、どのみち include の行が変わるので、改名で増える手間は小さい。
- 関数の名前は変えない（2 章「公開か内部かは、名前では区別しない」）。区別するのはファイルの名前だけである。
- インクルードガードは、パスから付ける（`CLOPTS_DECL_SCOPE_H` と `CLOPTS_SRC_DECL_SCOPE_INTERNAL_H`）。

公開ヘッダと同じ名前の内部ヘッダを置かないこと、`x_internal.h` には公開ヘッダ `x.h` があることは、`structure.names` で検査する。最初の include は、レビューで確かめる。

## 4. ディレクトリは依存の向きを表す

モジュールを分ける基準は、何に依存してよいかである。モジュールは名前空間ではない。

1. **ドメインを知らない部品は、いちばん下に置く。** 確保、サイズの計算、可変長配列、UTF-8 の読み取り、エラーの種類（不正な名前、重なり、衝突など）は、オプションもコマンドも知らない。
2. **OS に触るコードは 1 つのモジュールに集め、`*_win32.c` と `*_posix.c` に閉じ込める。** ほかのモジュールは、OS を知らないヘッダ越しにそれを使う。OS に触らずに書ける部分（コマンドラインの分割）は別のファイルにして、どの OS でもテストする。
3. **宣言は解析を知らない。解析は文面を知らない。**
4. **外側のモジュールは、公開ヘッダだけで中心を読む。** 文面のモジュールは、宣言と結果を公開の読み取り関数だけで読む。ライブラリの利用者が書けることしかしない。
5. **ファイルごとの例外は置かない。** 規則は「モジュール A はモジュール B を include できる」の形だけにする。

4 の裏返しとして、外側のモジュールが内部ヘッダを欲しがったら、公開 API に足りないものがある。文面が「コマンドの名前に隠れるグローバルオプション」を公開 API だけで判定しようとして、名前の照合の規則を書き直すことになるなら、足りないのは隠す判定の公開関数である。

5 の裏返しとして、例外が要るなら、置き場所が違っている。

依存してよいモジュールの内部ヘッダは include できる。

依存の向きは、テスト `structure.modules`（`tests/structure/check_structure.cmake`）で、`src/` と `include/clopts/` の両方について検査する。モジュールを足すとき、依存を変えるときは、検査の規則も同じ変更で直す。

## 5. 1 つの規則は 1 か所に書く

同じ規則が 2 か所に要るようになったら、書き写さない。その規則の持ち主である概念に関数を置き、両方から呼ぶ。

| 規則 | 持ち主 |
|------|--------|
| 書かれた名前がどのオプションを指すか（完全一致、次に `--no-<name>`。選ばれたコマンド、次にプログラム） | 宣言（Scope の中の照合と、Scope をまたぐ検索） |
| UTF-8 の並びの読み方（最短形、サロゲート、上限） | ドメインを知らない部品 |
| argv の 1 要素の形（`--`、`--name=value`、`-abc`） | 解析の字句の読み取り |

- 持ち主は、その規則を使うモジュールすべてが依存できる、いちばん上のモジュールに置く。
- 外側のモジュールが使うなら、公開の関数にする。
- 同じデータを読む経路も 1 本にする。公開の読み取り関数と、同じことをする内部の関数を、並べて持たない。同じ値を 2 つの型から読めるようにもしない。使い方エラーの起きたコマンドは、結果の選ばれたコマンドと同じなので、`clopts_result_get_command` だけで読む。

## 6. 作る途中のものと、できあがったものを分ける

1. できあがったものは、作ってから変えない。受け取る側には `const` で渡す。
2. 作る途中の状態は、別の型にする。できあがったものは、それを受け取って一度だけ作る。
3. できあがったものに「あとから設定する関数」（`set_error`、`finish`）が要るなら、途中の状態が混ざっている。

解析の結果は、利用者が読むだけの値である。解析が argv を読みながら書き足していく記録とは、別の型にする。宣言も同じで、組み立てている間はビルダー関数で書き、プログラムに渡した後は読むだけである。

### 同じに扱えるものだけを、共通の型にする

読むときと書くときで、共通にできる範囲が違うことがある。プログラムとコマンドは、どちらも「オプションと位置引数の並び」（Scope）を持ち、読み方は同じである。足すときの規則は持ち主ごとに違う（プログラムは、サブコマンドがあると位置引数を持てない）。

このときは、読み取りだけを共通の型（Scope）の関数にし、足す関数は持ち主に残す。足す関数まで共通の型に寄せると、持ち主ごとの規則を共通の型が知ることになる。

### 公開 API の形は、利用者が書くコードから決める

概念モデルは、内部の構成と語彙を決める。公開 API の形は、それとは別に、利用者が書くコードから決める。概念モデルをそのまま公開 API に写すと、利用者に要らない概念（まだどこにも付けていないオプション）と、その管理（所有権の受け渡し、失敗したときの後始末）が利用者のコードに出る。ほかの言語なら、メソッドをつなげる書き方、所有権の移動、例外が隠す手間も、C ではそのまま書くことになる。

公開 API を決めるときは、その API で書いたサンプル（`examples/`）を先に書き、行数と、どの行が何のためにあるかを見る。概念として自然かどうかは、内部の構成を決める基準で、公開 API の形を決める基準ではない。宣言の API でこれを取り違えた経緯は、[アーキテクチャ](architecture.md) の「宣言の API の形」にある。

## 7. エラーの種類は、ドメインを知らない語彙にする

ビルダー関数が返すエラー（`clopts_error_t`）は、errno の `EINVAL`、`EEXIST`、`ENOMEM` と同じく、何が起きたかの種類だけを表す。どの規則が破れたかは表さない。

1. 列挙子には、オプションやコマンドの語彙を入れない（`DUPLICATE`。`DUPLICATE_OPTION` にしない）。どの呼び出しがどの種類を返すかは、呼び出す側のモジュールが決める。
2. 種類を足すのは、今の種類のどれにも当てはまらないときだけである。新しい規則を足したら、まず今の種類（`NOT_APPLICABLE`、`CONFLICT`、`ORDER` など）に入れる。
3. 細かい理由を返すしくみ（どの属性とぶつかったか、などのデバッグ用の文）は置かない。要るようになってから考える。

理由は 3 つある。

- **エラーの型を base に置ける。** 語彙がドメインを知らなければ、エラーの型はいちばん下のモジュールの部品になり、4 章の 1 と矛盾しない。宣言の規則ごとの列挙子は、base にオプションの知識を持ち込む。
- **宣言エラーは、プログラマの誤りである。** 開発中に一度出て、直せば二度と出ない。利用者が実行時に種類で分岐することは、まずない。そのため、ビルダー関数は誤りを戻り値で返さず、プログラムが最初の 1 つを覚える（`clopts_program_get_error`）。利用者は宣言の後で 1 回だけ確かめる。呼び出しごとに確かめさせると、製品のコードが、直せば二度と出ない誤りの検査で埋まる。
- **規則を足しても、公開の列挙が増えない。** 規則ごとに列挙子を足すと、宣言の規則を変えるたびに公開 API と ABI が変わる。

## 8. src に置かないもの

- **テストだけが使う経路。** テストのために本体に入口を足さない。テストは、公開 API か、本体も使っている内部の関数を呼ぶ。
- **互換のための別名、移行用の関数、古い名前。** `AGENTS.md` のとおりである。
- **利用者が公開 API で短く書けて、書くプログラムが少ないこと。** `help` コマンドを作る関数は置かない。一方、ほぼすべてのプログラムが毎回書くものは、短く書けても置く（`clopts_program_add_help_option`）。線を引くのは「短く書けるか」ではなく「ほぼ全員が毎回書くか」である。全員が同じ 10 行を書くなら、その 10 行はライブラリが持つ（[アーキテクチャ](architecture.md)の「設計の判断」）。

## 9. 迷ったときの問い

1. これは何という概念か。1 語で言えるか。言えないなら、2 つのものが混ざっていないか。
2. その名前のファイルは、もうあるか。あればそこに置く。なければ `x.c` と `x.h` を作る。
3. モジュールの名前を外しても、名前はぶつからないか。ぶつかるなら、概念を分け直す。
4. 何に依存するか。OS に触るか。宣言を知るか。結果を知るか。置くモジュールは、それで決まる。
5. 同じ規則を、別の場所にもう書いていないか。
6. 公開の関数なら、ヘッダと同じ名前の `.c` で定義できるか。できないなら、置くモジュールか名前が違う。
7. 規則に例外を足そうとしていないか。
8. 例外をなくすために、規則をその根拠の外まで広げていないか。
9. エラーの種類を足すなら、今の種類のどれにも当てはまらないか。列挙子にドメインの語が入っていないか。

## 10. 採らなかった案

| 案 | 採らなかった理由 |
|----|------------------|
| 公開ヘッダと同じ名前の内部ヘッダ（`src/decl/scope.h` と `clopts/decl/scope.h`） | エディタの検索やタブ、コンパイラのメッセージで、どちらの面かがパスまで読まないと分からない。公開と内部の間で関数を動かすときは include の行がどのみち変わるので、名前を同じにしても手間は減らない |
| すべての内部ヘッダに `_internal` を付ける | `src/` にあることで内部だと分かるので、印が何も伝えない。公開の面を持つかどうかが、ファイル名から読めなくなる |
| ほかのモジュールに見せる内部ヘッダを列挙する | モジュールの依存の向きの規則と二重になる |
| 構造体の中身を見せる相手を絞る実装ヘッダ（`x_impl.h`）を、内部ヘッダと別に置く | 1 つの概念に内部ヘッダが 2 つでき、どちらを include するか、関数をどちらに置くかの判断が増える。実際には、中身を見せない側の内部ヘッダを include するファイルも同じモジュールにしかなく、分けても守れるものがなかった。書き換えの制限は、型の説明で足りる |
| 公開ヘッダを平置きにする（`include/clopts/*.h`） | 公開ヘッダと `.c` の対応が、パスから読めない。公開ヘッダどうしの依存の向きを検査できない |
| モジュールごとの全部入りヘッダ（`decl.h`） | `clopts/decl/program.h` が宣言のヘッダをすべて include する。全部入りは `clopts.h` の 1 つで足りる |
| `src/` を平置きにする | この規模なら可能だが、依存の向きを機械的に検査するために、ディレクトリを使う |
| 層をまたぐ関数を置く `src/clopts.c` | どのモジュールにも属さないファイルは、依存の規則の外になる |
| OS のモジュールを公開 API の上に置き、`clopts_parse` をそこで定義する | 解析は OS のモジュールに依存しなくなるが、`clopts_parse` と `clopts_parse_with_env` が別のモジュールに分かれる。公開ヘッダも 2 つに分かれる。どちらかを改名すると、いちばん使う入口の名前が長くなる |
| OS ごとに 1 ファイルにする（`win32.c`、`posix.c`） | 接頭辞からファイルが決まらない。`clopts_argv_create` の定義が、名前から引けない |
| Scope に足す操作も公開する（`clopts_scope_add_option`） | 6 章のとおり。組み立て用（非 `const`）と読み取り用（`const`）で、Scope を得る関数も 2 つ要る |
| 名前からオプションを引く、汎用の公開関数 | `--no-<name>` の形の名前を、確保なしでは渡せない。外側のモジュールに要るのは、隠す判定だけである |
| プログラム自身の範囲を Command で表す、コマンドを入れ子にする | [アーキテクチャ](architecture.md)の「設計の判断」のとおり |
| オプションを単独で作り、設定してから渡す（`clopts_option_create` と、作ったものを受け取る `clopts_program_add_option`） | 操作の概念としては自然だが、利用者のコードに所有権の受け渡しと後始末が出る。6 章「公開 API の形は、利用者が書くコードから決める」と、[アーキテクチャ](architecture.md)の「宣言の API の形」のとおり |
| ビルダー関数が、宣言の誤りを呼び出しごとに戻り値で返す | 7 章のとおり。誤りのほとんどはプログラマの誤りで、毎回確かめる理由がない |

## 11. 参考にした設計

| ライブラリ | 取り入れた点 |
|------------|--------------|
| Lua | 概念ごとに `.c`、`.h`、接頭辞を 1 組にする（`ltable.c`、`ltable.h`、`luaH_`）。CLOpts は、接頭辞で縛るのを構造体とその操作の組に絞る。補助ライブラリ `lauxlib` は、公開 API だけで書く（文面のモジュール） |
| cairo | 誤りを文脈が覚え、誤りの後の呼び出しは何もしない。利用者は最後に 1 回確かめる（`clopts_program_get_error`） |
| argtable3 | C で、ハンドルを返す関数で宣言を組み立て、確保の失敗は最後に 1 回確かめる。結果は宣言のハンドルから読む |
| LLVM | 公開ヘッダとソースを、同じ形のディレクトリに置く（`include/llvm/Support/` と `lib/Support/`）。表現を見せるヘッダを別にする（`LLVMContextImpl.h`、`AttributeImpl.h`）。CLOpts は表現を見せるヘッダを別にせず、内部ヘッダ 1 つに置く（3 章「内部ヘッダの種類」） |
| libgit2 | 内部ヘッダが、公開ヘッダを include して構造体の中身と内部の関数を足す（`include/git2/repository.h` と `src/libgit2/repository.h`）。ただし libgit2 は内部ヘッダを公開ヘッダと同じ名前にし、内部の関数を `git_repository__*` と名前で区別する。CLOpts は逆に、ヘッダのファイル名で区別し（`x_internal.h`）、関数の名前では区別しない |
| CPython | ヘッダを見せる相手で段に分ける（公開 API、CPython 固有の API、内部 API） |
| GLib / GObject | 実装を見せるヘッダを別にする（`*-private.h`） |
| SQLite | 中心は OS の関数を呼ばない。OS ごとの実装を、OS を知らないヘッダ越しに使う（`os.h` と、`os_unix.c`、`os_win.c`） |
| clap（Rust） | 宣言、解析、出力の分け方。字句の読み取りを別の部品にする（`clap_lex`）。解析が記録するもの（`ArgMatches`）と、解析の結果を分ける |
| glibc argp | 解析、ヘルプ、整形つきの出力先（`argp-fmtstream`）を分ける |
